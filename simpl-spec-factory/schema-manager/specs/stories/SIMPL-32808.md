# SIMPL-32808: [ENHANCE][UI] - Governance Authority – providing details of a new version of an existing schema via UI
- Status: DevTeam PBI is ready for Implementation check
- Type: Story
- Created: 2026-09-08, updated: 2026-10-15
- Source: https://jira.simplprogramme.eu/browse/SIMPL-32808 (collected 2026-10-28)

## Description and acceptance criteria

**As a** Governance Authority user,

**I want** to provide the details for a new version of an existing schema through UI,

**So that** I can create a new schema version with new content while preserving its history.

## Acceptance Criteria

### Positive Scenario: Successfully creating a new version

**Given** I am authenticated as a Governance Authority user, with a role authorising schema management

**And** I am viewing the details page for a specific schema.

**When** I initiate the "Create New Version" action (e.g., by clicking a button).

**And** I fill in changelog message but do not fill schemaType

**And** I upload a valid schema definition file (e.g., a `.ttl` file).

**And** I submit the form.

**Then** the UI shall send a `POST` request to the `/schemas/{schemaName}/versions` endpoint with the form data as `multipart/form-data where schemaType was set to "RESOURCE" as default value`

**And** the service shall respond with a `201 Created` HTTP status.

**And** I should be redirected back to the schema's detail page, where the newly created version is now visible in the version list.

**Given** I am a logged-in user with the `governance-admin` role.

**And** I am viewing the details page for a specific schema.

**When** I initiate the "Create New Version" action (e.g., by clicking a button).

**And** I fill in all required fields in the form, i.e. a changelog message and schemaType field (either RESOURCE or SEARCH)

**And** I upload a valid schema definition file (e.g., a `.ttl` file).

**And** I submit the form.

**Then** the UI shall send a `POST` request to the `/schemas/{schemaName}/versions` endpoint with the form data as `multipart/form-data`.

**And** the service shall respond with a `201 Created` HTTP status.

**And** I should be redirected back to the schema's detail page, where the newly created version is now visible in the version list.

**Given** I am authenticated as a Governance Authority user, with a role authorising schema management

**And** I am viewing the details page for the federated search schema.

**When** I initiate the "Create New Version" action (e.g., by clicking a button).

**And** I fill in all required fields in the form, i.e. a changelog message and schemaType = SEARCH

**And** I upload a valid schema definition file (e.g., a `.ttl` file).

**And** I submit the form.

**Then** the UI shall send a `POST` request to the `/schemas/{schemaName}/versions` endpoint with the form data as `multipart/form-data`.

**And** the service shall respond with a `201 Created` HTTP status.\
**And** I should be redirected back to the schema's detail page, where the newly created version is now visible in the version list.

### Negative Scenario: Front-end validation failure

**Given** I am on the "Create New Version" form.

**When** I leave the changelog blank, or do not upload a file.

**Then** the UI shall display clear, inline validation error messages next to the corresponding fields.

**And** the form submission button shall be disabled until all validation errors are corrected.

### Negative Scenario: API returns an error

**Given** I have submitted the "Create New Version" form with valid inputs.

**When** the API responds with an error, such as `400 Bad Request` (e.g., for an invalid SHACL file) or `409 Conflict` (if a former version for the given schemaType does not exist).

**Then** I should remain on the form.

**And** the UI shall display a clear, user-friendly error message at the top of the form explaining the specific reason for the failure (e.g., "The uploaded schema file is invalid").

Technical Info:

In R25 schema management was enhanced by introducing a new schema type for defining Federated Search Schema. Therefore a new attribute schemaType is introduced to distinguish between two types: RESOURCE and SEARCH. RESOURCE refers to the former existing schema definitions used to describe resource definitions. Hence as default value if schema type is not explicitely mentioned the schema type should be considered to be RESOURCE. For schema type SEARCH there will be due to ADR-008 only one schema definition.\
- enhance UI dialog with a new entry field (selection box) for schemaType with two possible options (RESOURCE or SEARCH)\
- enhance existing solution by adding new attribute schematype to distinguish RESOURCE for already implemented solution and "SEARCH" for Federated Search schemas. Ensure by explicitely setting filter for schemaType = RESOURCE for existing test cases they still work.\
