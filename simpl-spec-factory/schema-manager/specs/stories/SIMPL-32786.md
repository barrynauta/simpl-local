# SIMPL-32786: ENHANCE - Governance Authority - retrieving metadata for all versions of a schema via API

## Description and acceptance criteria

**As a** Governance Authority,

**I want** to retrieve a list of all available versions for a specific schema via API,

**So that** I can review its entire version history, change logs, and metadata.

Acceptance Criteria:

Path retrieve all versions for schema type = RESOURCE when not specifying optional filter for schema type (Default value for schema type is RESOURCE)\
**Given** I am an API client with a valid authentication token granting the `GA_SCHEMA_VIEWER or GA_SCHEMA_ADMIN` role.

**And** I have the name of an existing schema (e.g., `InfrastructureSchema`).

**When** I send a `GET` request to the `/schemas/{schemaName}/versions` endpoint.\
**And** I do not set the optional filter for schema type or resource type

**Then** the service shall respond with a `200 OK` HTTP status.

**And** the response body must be a paginated list of schema versions (20 items/page by default - see pagination guidelines [https://www.belgif.be/specification/rest/api-guide/#pagination])\
**And** the filter is set to schema type = RESOURCE\
**And** each schema version in the list must include all its metadata

Path retrieve all versions for schema type = SEARCH\
**Given** I am an API client with a valid authentication token granting the `GA_SCHEMA_VIEWER or GA_SCHEMA_ADMIN` role.

**And** I have the name of an existing federated search schema (e.g., `SearchSchema`).

**When** I send a `GET` request to the `/schemas/{schemaName}/versions` endpoint.\
**And** I set the optional filter for schema type = SEARCH

**Then** the service shall respond with a `200 OK` HTTP status.

**And** the response body must be a paginated list of schema versions for federated Search only with matching schema name (20 items/page by default - see pagination guidelines [https://www.belgif.be/specification/rest/api-guide/#pagination])\
**And** each schema version in the list must include all its metadata

Negative Scenarios:\
**Given** I am an API client with a valid and authorized token.

**When** I send a `GET` request to `/schemas/{schemaName}/versions` where {schemaName} contains illegal characters (e.g., `Infrastructure$chema!`). (Schema name must be `PascalCase`. Alphanumeric only. Min 3, Max 64 chars. No spaces or special characters.)

**Then** the service shall respond with a `400 Bad Request` HTTP status.\
**And** the response body should contain a descriptive error message about the invalid format.

—\
**Given** I am an API client with a valid authentication token granting the `GA_SCHEMA_VIEWER` role.

**And** I have a schema name that is correctly formatted but does not exist in the system (e.g., "UnknownSchema").

**When** I send a `GET` request to the `/schemas/UnknownSchema/versions` endpoint.

**Then** the service shall respond with a `404 Not Found` HTTP status.

Technical Design:\
This US is covered with the implementation of [https://jira.simplprogramme.eu/browse/SIMPL-33537](https://jira.simplprogramme.eu/browse/SIMPL-33537) and only for linkage to the epic.

Technical Documentation:\
* No difference in behaviour for federated search schemas or resource definition schemas\
* the filter for schema type is optional and should be set by default to RESOURCE to cover the former use cases.\
* enhance existing solution by adding new attribute schematype to distinguish RESOURCE for already implemented solution and "SEARCH" for Federated Search schemas. Ensure by explicitely setting filter for schemaType = RESOURCE for existing test cases they still work.\
