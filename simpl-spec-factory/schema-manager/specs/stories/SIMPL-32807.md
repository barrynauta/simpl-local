# SIMPL-32807: [ENHANCE] - Governance Authority – providing details of a new version of an existing schema via API
- Status: DevTeam PBI In Progress
- Type: Story
- Created: 2026-09-08, updated: 2026-10-20
- Source: https://jira.simplprogramme.eu/browse/SIMPL-32807 (collected 2026-10-28)

## Description and acceptance criteria

**As a** Governance Authority administrator,\
**I want** to submit a new version of an existing schema by providing a changelog, and a new definition file via the API,\
**So that** I can update a schema with new properties or constraints while maintaining a full version history.\
Acceptance Criteria:\
Positive Scenario

Path: Updating existing Resource Definition Schema with default value\
**Given** I am an API client with a valid authentication token granting the `GA_SCHEMA_ADMIN` role,\
**And** a schema with the name ` \{schemaName}` already exists for schema type = RESOURCE,\
**And** the latest version of that schema can be uniquely identified by its status PUBLISHED\
**When** I send a `POST` request to the `/schemas/\{schemaName}/versions` endpoint with a `multipart/form-data` body containing:\
- schemaType is empty\
- A `metadata` part with schemaName, schemaType and a `changelog` description.\
- A `file` part containing a valid SHACL definition in a `.ttl` file.\
**Then** the new schema version is stored with the provided metadata and SHACL definition for schemaType="RESOURCE"\
**And** the new schema version has status PUBLISHED\
**And** the status of the previous version (was the latest before) has changed from PUBLISHED to REVOKED\
**And** the service responds with a `201 Created` HTTP status.\
**And** the response `Location` header contains the URI for the newly created schema version.\
**And** the response body contains the full resource metadata representation of the new version.

Path: Updating existing Resource Definition Schema with explicitely set schema type\
**Given** I am an API client with a valid authentication token granting the `GA_SCHEMA_ADMIN` role,\
**And** a schema with the name ` \{schemaName}` already exists for schema type = RESOURCE,\
**And** the latest version of that schema can be uniquely identified by its status PUBLISHED\
**When** I send a `POST` request to the `/schemas/\{schemaName}/versions` endpoint with a `multipart/form-data` body containing:\
- schemaType = RESOURCE\
- A `metadata` part with schemaName, schemaType and a `changelog` description.\
- A `file` part containing a valid SHACL definition in a `.ttl` file.\
**Then** the new schema version is stored with the provided metadata and SHACL definition for schemaType="RESOURCE"\
**And** the new schema version has status PUBLISHED\
**And** the status of the previous version (was the latest before) has changed from PUBLISHED to REVOKED\
**And** the service responds with a `201 Created` HTTP status.\
**And** the response `Location` header contains the URI for the newly created schema version.\
**And** the response body contains the full resource metadata representation of the new version.

Path: Updating existing Federated Search Schema\

**And** a schema with the name ` \{schemaName}` already exists for schema type = SEARCH,\
**And** the latest version of that schema can be uniquely identified by its status PUBLISHED\

Negative Scenarios

Path: Updating not existing Resource Definition Schema\
**Given** I am an API client with a valid authentication token,\
**And** the ** schema with name `\{nonExistantSchemaName}` doesn't exist for schema type = RESOURCE\
**When** I send a `POST` request to the `/schemas/\{schemaName}/versions` endpoint with a `multipart/form-data` body containing:\
- ** schemaType is empty\
- A `metadata` part with not existing schemaName and a `changelog` description.\
- A `file` part containing a valid SHACL definition in a `.ttl` file.\
**Then** the service shall respond with a `404 Not Found` HTTP status.

Path: Updating not existing Federated Search Schema\
**Given** I am an API client with a valid authentication token,\
**And** the ** schema with name `\{nonExistantSchemaName}` doesn't exist for schema type = SEARCH\
**When** I send a `POST` request to the `/schemas/\{schemaName}/versions` endpoint with a `multipart/form-data` body containing:\
- ** schemaType = SEARCH\
- A `metadata` part with not existing schemaName and a `changelog` description.\
- A `file` part containing a valid SHACL definition in a `.ttl` file.\
**Then** the service shall respond with a `404 Not Found` HTTP status.

Path: Updating not existing Federated Search Schema, but Resource Definition of given schema name\
**Given** I am an API client with a valid authentication token granting the `GA_SCHEMA_ADMIN` role,\
**And** a schema with the name ` \{schemaName}`does not exist for schema type = RESOURCE, but for schema type = SEARCH,\
**And** a version number of it: `\{schemaVersion}` that already exists\
**When** I send a `POST` request to `/schemas/\{schemaName}/versions` with a `multipart/form-data` body containing:\
- ** schemaType = SEARCH\
- A `metadata` part with not existing schemaName and a `changelog` description.\
- A `file` part containing a valid SHACL definition in a `.ttl` file.\
**Then** the service shall respond with a `404 Not Found` HTTP status.

Path: Updating existing schema with invalid SHACL file.\
**Given** I am an API client with a valid authentication token granting the `GA_SCHEMA_ADMIN` role,\
**And** a schema with the name ` \{schemaName}` already exists for schema type = RESOURCE,\
**And** the latest version of that schema can be uniquely identified by its status PUBLISHED\
**And** I have an invalid SHACL file\
**When** I send a `POST` request to `/schemas/ \{schemaName}/versions` with a `multipart/form-data` body containing:\
- * schemaType is not explicitely set (default Value is RESOURCE)\
- A `metadata` part with existing schemaName and a `changelog` description.\
- A `file` part containing an invalid SHACL definition in a `.ttl` file.\
**Then** the service shall respond with a `400 Bad Request` HTTP status,\
**And** the response body shall contain a problem details JSON object explaining the validation error.

-\
**Given** I am an API client with a valid authentication token granting the `GA_SCHEMA_ADMIN` role,\
**And** I have a valid SHACL file\
**And** malformed metadata (missing changelog),\
**When** I send a `POST` request to `/schemas/ \{schemaName}/versions` with said SHACL file and metadata\
**Then** the service shall respond with a `400 Bad Request` HTTP status,\
**And** the response body shall contain a problem details JSON object explaining the validation error.

-\
**Given** I am an authenticated API client\
**When** an unexpected server-side error occurs while processing the request\
**Then** the system must return Internal Server Error\
**And** the service shall respond with a `500 Error` HTTP Status
