# SIMPL-32802: [ENHANCE] - Governance Authority – providing details of a new schema via an API

- Created: 2026-09-08, updated: 2026-10-13
- Source: https://jira.simplprogramme.eu/browse/SIMPL-32802 (collected 2026-10-28)

## Description and acceptance criteria

**As a** Governance Authority administrator,

**I want** to submit the definition for a new schema by providing its core metadata and its initial SHACL content via a single API call,

**So that** I can have the system create the schema concept and automatically establish its first version using an algorithm.

Acceptance Criteria:

PATH: Create a new Resource Definition Schema with default options\
**Given** I am an API client authenticated with the GA_SCHEMA_ADMIN role,

**And** I want to define a new schema of schemaType = RESOURCE

**And** I have the required metadata for the new schema concept (e.g., {"name": "DataAsset", "title": "Data Asset", "description": "Describes a discoverable dataset.", "resourceType": "data"}) not explicitely specifying schema type

**And** I have a valid SHACL schema definition saved in a .ttl file.

**When** I send a POST request to the /api/v1/schemas endpoint with the .ttl file and the JSON metadata as multipart/form-data.

**Then** the Schema Management Service (SMS) shall validate the syntax and integrity of the submitted SHACL file.

**And** if validation is successful, the service shall create a new schema concept using the provided metadata.

**And** the service shall automatically create an initial schema version according pre-defined standards and store the submitted SHACL file as its content.

**And** the service shall respond with a 201 Created HTTP status and include a Location header pointing to the URI of the newly created schema concept resource.

PATH: Create initial Federated Search Schema\
**Given** I am an API client authenticated with the GA_SCHEMA_ADMIN role,\
**And** there is no previous published federated search schema

**And** I want to define a new schema of schemaType = SEARCH

**And** I have the required metadata for the new schema concept (e.g., {"name": "DataAsset", "title": "Data Asset", "description": "Describes a discoverable dataset.", "resourceType": NULL}). set explicitely schema type = SEARCH

**And** I have a valid SHACL schema definition saved in a .ttl file.

**When** I send a POST request to the /api/v1/schemas endpoint with the .ttl file and the JSON metadata as multipart/form-data.

**Then** the Schema Management Service (SMS) shall validate the syntax and integrity of the submitted SHACL file.

**And** if validation is successful, the service shall create a new schema concept using the provided metadata.

**And** the service shall automatically create an initial schema version according pre-defined standards and store the submitted SHACL file as its content.

**And** the service shall respond with a 201 Created HTTP status and include a Location header pointing to the URI of the newly created schema concept resource.

Negative Scenarios:

PATH: Specifying resource type for schema type = SEARCH\
**Given** I am an API client authenticated with the GA_SCHEMA_ADMIN role,\
**And** there is no previous published federated search schema

**And** I want to define a new schema of schemaType = SEARCH

**And** I have the required metadata for the new schema concept (e.g., {"name": "DataAsset", "title": "Data Asset", "description": "Describes a discoverable dataset.", "resourceType": not null}). set explicitely schema type = SEARCH

**And** I have a valid SHACL schema definition saved in a .ttl file.

**When** I send a POST request to the /api/v1/schemas endpoint with the .ttl file and the JSON metadata as multipart/form-data.

**Then** the service shall respond with a 400 Bad request HTTP status.\
**And** the service shall not create a new schema concept or version.

PATH: Update an already existing Resource Definition Schema\
**Given** I am an API client authenticated with the GA_SCHEMA_ADMIN role,\
**And** I have metadata for a new schema.\
**And** I want to create a new schema with schemaType="RESOURCE"\
**And** a schema with the same name as in the metadata and same resourceType already exists in the system for schema type = RESOURCE.

**When** I send a POST request to /api/v1/schemas with the schema metadata and a valid SHACL file.

**Then** the service shall respond with a 409 Conflict HTTP status.

**And** the service shall not create a new schema concept or version.

PATH: Update an already existing Federated Search Schema\
**Given** I am an API client authenticated with the GA_SCHEMA_ADMIN role,\
**And** I have metadata for a new schema.\
**And** I want to create a new schema with schemaType="SEARCH"\
**And** a schema with the same name as in the metadata already exists in the system for schema type = SEARCH.

**When** I send a POST request to /api/v1/schemas with the schema metadata and a valid SHACL file and schemaType = "SEARCH".

**Then** the service shall respond with a 409 Conflict HTTP status.

**And** the service shall not create a new schema concept or version.

PATH: Create new Federated Search Schema where another published Federated Search Schema exists\
**Given** I am an API client authenticated with the GA_SCHEMA_ADMIN role,\
**And** I have metadata for a new schema.\
**And** I want to create a new schema with schemaType="SEARCH"\
**And** a published federated search schema with another name as in the metadata already exists in the system for schema type = SEARCH.

**When** I send a POST request to /api/v1/schemas with the schema metadata and a valid SHACL file and schemaType = "SEARCH".

**Then** the service shall respond with a 409 Config HTTP status.

**And** the service shall not create a new schema concept or version.

Path: sending an invalid SHACL file\
**Given** I am an API client authenticated with the GA_SCHEMA_ADMIN role,

**And** I have metadata for a new schema.

**And** I have a SHACL schema definition file that contains syntax errors.

**When** I send a POST request to /api/v1/schemas with the invalid .ttl file and the JSON metadata.

**Then** the service shall respond with a 400 Bad Request HTTP status.

**And** the response body shall contain a structured error message detailing the validation failure.

**And** the service shall not create a new schema concept or version.

Technical Info:\
* enhance existing solution by adding new attribute schematype to distinguish RESOURCE for already implemented solution and "SEARCH" for Federated Search schemas. Ensure by explicitely setting filter for schemaType = RESOURCE for existing test cases they still work.\
* for schemaType="RESOURCE" the attribute resourceType (APP, INFRA, DATA) is mandatory, for schemaType="SEARCH" the attribute resourceType must be unspecified (NULL), as it is valid for all resourceTypes.\
* For schemaType="SEARCH" according to ADR-008 there must only one federated Search Schema defined. The uniqueness key is one published SEARCH schema globally, regardless of name; state that revoked schemas remain addressable as history, and define whether a new schema may reuse a revoked schema's name.\
