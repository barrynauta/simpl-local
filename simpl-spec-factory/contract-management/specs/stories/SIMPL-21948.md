# SIMPL-21948: Consumer validates the usage contract signed by the Provider
- Status: DevTeam PBI blocked
- Type: Story
- Created: 2025-12-08, updated: 2026-10-23
- Source: https://jira.simplprogramme.eu/browse/SIMPL-21948 (collected 2026-10-29)

## Description and acceptance criteria

Clarified Description

**As a** Consumer,\
**I want** the Consumer Contract Manager to validate the usage contract signed by the Provider,\
**So that** the contract can be accepted for further processing only if the Provider signature and contract content are valid.

This story covers automatic backend validation of the Provider signed usage contract in the Consumer Contract Manager.

The validation is performed asynchronously.

The current implementation does not expose a synchronous validation API where the caller waits for the final validation result in the same request.

Instead, the validation process is triggered by the backend flow after the Consumer Contract Manager receives the Provider signed contract data. The validation result is persisted as contract state and can be verified by checking the resulting contract status, validation result, logs or related backend state.

Scope\
- Validate the Provider digital signature.

- Validate that the signed payload matches the expected contract content.

- Validate that the Provider identity or credential information is acceptable.

- Validate that the contract is within the allowed validity period.

- Persist the validation result.

- Update the contract state according to the validation outcome.

- Log the validation process with technical traceability.

Out of scope\
- Manual UI validation.

- Synchronous validation response with final business result.

- User authentication and authorization checks for a manual validation action.

- Changing the signing process.

- Creating a new validation API if the existing implementation is event driven.

- Policy enforcement unrelated to validation of the signed contract.

Expected asynchronous flow\
- Consumer Contract Manager receives Provider signed contract data.

- Backend flow triggers contract validation automatically.

- Consumer Contract Manager validates the Provider signature and contract content.

- Consumer Contract Manager persists the validation result.

- Consumer Contract Manager updates the contract status according to the validation outcome.

- Validation result is available through backend state, logs or contract details.

Acceptance Criteria

AC1 Successful asynchronous validation

**Given** the Consumer Contract Manager has received the usage contract signed by the Provider\
**And** the Provider signature is valid\
**And** the signed payload matches the expected contract content\
**And** the Provider identity or credential information is valid\
**And** the contract is within its validity period\
**When** the asynchronous validation process is completed\
**Then** the validation result is marked as successful\
**And** the contract status is updated according to the agreed lifecycle\
**And** the validation result is persisted\
**And** the validation is traceable in backend logs.

AC2 Invalid Provider signature

**Given** the Consumer Contract Manager has received the usage contract signed by the Provider\
**When** the Provider signature validation fails\
**Then** the validation result is marked as rejected or failed\
**And** the contract is not marked as successfully validated\
**And** the rejection reason indicates invalid Provider signature\
**And** the failure is traceable in backend logs.

AC3 Payload integrity mismatch

**Given** the Consumer Contract Manager has received the usage contract signed by the Provider\
**When** the signed payload does not match the expected contract content\
**Then** the validation result is marked as rejected or failed\
**And** the contract is not marked as successfully validated\
**And** the rejection reason indicates payload integrity mismatch\
**And** the failure is traceable in backend logs.

AC4 Contract expired or not yet valid

**Given** the Consumer Contract Manager has received the usage contract signed by the Provider\
**When** the contract validity period is outside the allowed timeframe\
**Then** the validation result is marked as rejected or failed\
**And** the contract is not marked as successfully validated\
**And** the rejection reason indicates contract validity issue\
**And** the failure is traceable in backend logs.

AC5 Provider credential revoked or untrusted

**Given** the Consumer Contract Manager has received the usage contract signed by the Provider\
**When** the Provider credential or trust chain is revoked, invalid or untrusted\
**Then** the validation result is marked as rejected or failed\
**And** the contract is not marked as successfully validated\
**And** the rejection reason indicates Provider credential or trust issue\
**And** the failure is traceable in backend logs.

AC6 Schema or content validation failure

**Given** the Consumer Contract Manager has received the usage contract signed by the Provider\
**When** required fields are missing or the signed contract content does not match the expected structure\
**Then** the validation result is marked as rejected or failed\
**And** the contract is not marked as successfully validated\
**And** the rejection reason indicates schema or content validation issue\
**And** the failure is traceable in backend logs.

AC7 Duplicate or replayed submission

**Given** the Consumer Contract Manager has already processed the same Provider signed contract\
**When** the same signed contract is received again\
**Then** the contract is not processed as a new successful validation\
**And** the duplicate or replayed submission is detected\
**And** the situation is traceable in backend logs.

AC8 Technical error during validation

**Given** the Consumer Contract Manager has received the usage contract signed by the Provider\
**When** a technical error occurs during asynchronous validation\
**Then** the validation result is marked as failed or remains pending according to the agreed lifecycle\
**And** the contract is not marked as successfully validated\
**And** the failure is traceable in backend logs.

AC9 Missing contract data

**Given** the asynchronous validation process is triggered\
**When** the required contract data is missing\
**Then** the validation result is marked as rejected or failed\
**And** the contract is not marked as successfully validated\
**And** the rejection reason indicates missing contract data\
**And** the failure is traceable in backend logs.

AC10 Asynchronous validation model

**Given** the validation process is implemented asynchronously\
**When** the validation is triggered\
**Then** the final validation result is not expected to be returned synchronously in the triggering request\
**And** validation must be verified through persisted backend state, contract status, validation result, logs or related contract details.

Technical info

The validation process is implemented as asynchronous backend processing.

Previous acceptance criteria expected synchronous API behaviour, but this does not match the implemented architecture.

Validation should therefore be tested by observing the resulting contract state, validation result and backend logs rather than expecting the final validation result in the same synchronous API response.

HTTP response codes in this story should not be treated as the primary validation mechanism unless a specific synchronous API endpoint is introduced or confirmed.

If PSO requires direct API based validation, the relevant OpenAPI endpoint must be confirmed separately.

Consumer side = Consumer Contract Management side / agreed backend flow, not necessarily direct physical contract delivery to Contract Manager.

Note:

“Provider-signed usage contract is available on the Consumer side” means that the Consumer side has access to the finalized Provider-signed contract through the agreed contract establishment flow and can validate it against the original request.

This should not be interpreted as a specific low-level delivery mechanism to one internal component only.

After finalization, the Consumer side must keep its own contract copy/state/evidence required to consult and validate the finalized usage contract.
