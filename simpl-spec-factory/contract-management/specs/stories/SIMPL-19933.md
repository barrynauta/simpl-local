# SIMPL-19933: Provider Contract Manager to validate the usage contract offer signed by the Consumer
- Status: DevTeam PBI blocked
- Type: Story
- Created: 2025-10-24, updated: 2026-10-20
- Source: https://jira.simplprogramme.eu/browse/SIMPL-19933 (collected 2026-10-29)

## Description and acceptance criteria

Clarified Description

**As a** Provider,\
**I want** the Provider Contract Manager to validate the usage contract offer signed by the Consumer,\
**So that** the contract offer can be accepted for further Provider side processing only if the Consumer signature and contract content are valid.

This story covers automatic backend validation of the Consumer signed usage contract offer in the Provider Contract Manager.

The validation is performed asynchronously.

The current implementation does not expose a synchronous validation API where the caller waits for the final validation result in the same request.

Instead, the validation process is triggered by the backend flow after the Provider Contract Manager receives the Consumer signed contract offer data. The validation result is persisted as contract state and can be verified by checking the resulting contract status, validation result, logs or related backend state.

Scope\
- Validate the Consumer digital signature.

- Validate that the signed payload matches the expected contract offer content.

- Validate that the Consumer identity or credential information is acceptable.

- Validate that the contract offer is within the allowed validity period.

- Persist the validation result.

- Update the contract negotiation state according to the validation outcome.

- Log the validation process with technical traceability.

Out of scope\
- Manual UI validation.

- Synchronous validation response with final business result.

- User authentication and authorization checks for a manual validation action.

- Changing the signing process.

- Creating a new validation API if the existing implementation is event driven.

- Policy enforcement unrelated to validation of the signed contract offer.

Expected asynchronous flow\
- Provider Contract Manager receives Consumer signed contract offer data.

- Backend flow triggers contract offer validation automatically.

- Provider Contract Manager validates the Consumer signature and contract offer content.

- Provider Contract Manager persists the validation result.

- Provider Contract Manager updates the contract negotiation status according to the validation outcome.

- Validation result is available through backend state, logs or contract details.

Acceptance Criteria

AC1 Successful asynchronous validation

**Given** the Provider Contract Manager has received the usage contract offer signed by the Consumer\
**And** the Consumer signature is valid\
**And** the signed payload matches the expected contract offer content\
**And** the Consumer identity or credential information is valid\
**And** the contract offer is within its validity period\
**When** the asynchronous validation process is completed\
**Then** the validation result is marked as successful\
**And** the contract negotiation status is updated according to the agreed lifecycle\
**And** the validation result is persisted\
**And** the validation is traceable in backend logs.

AC2 Invalid Consumer signature

**Given** the Provider Contract Manager has received the usage contract offer signed by the Consumer\
**When** the Consumer signature validation fails\
**Then** the validation result is marked as rejected or failed\
**And** the contract offer is not marked as successfully validated\
**And** the rejection reason indicates invalid Consumer signature\
**And** the failure is traceable in backend logs.

AC3 Payload integrity mismatch

**Given** the Provider Contract Manager has received the usage contract offer signed by the Consumer\
**When** the signed payload does not match the expected contract offer content\
**Then** the validation result is marked as rejected or failed\
**And** the contract offer is not marked as successfully validated\
**And** the rejection reason indicates payload integrity mismatch\
**And** the failure is traceable in backend logs.

AC4 Contract offer expired or not yet valid

**Given** the Provider Contract Manager has received the usage contract offer signed by the Consumer\
**When** the contract offer validity period is outside the allowed timeframe\
**Then** the validation result is marked as rejected or failed\
**And** the contract offer is not marked as successfully validated\
**And** the rejection reason indicates contract offer validity issue\
**And** the failure is traceable in backend logs.

AC5 Consumer credential revoked or untrusted

**Given** the Provider Contract Manager has received the usage contract offer signed by the Consumer\
**When** the Consumer credential or trust chain is revoked, invalid or untrusted\
**Then** the validation result is marked as rejected or failed\
**And** the contract offer is not marked as successfully validated\
**And** the rejection reason indicates Consumer credential or trust issue\
**And** the failure is traceable in backend logs.

AC6 Schema or content validation failure

**Given** the Provider Contract Manager has received the usage contract offer signed by the Consumer\
**When** required fields are missing or the signed contract offer content does not match the expected structure\
**Then** the validation result is marked as rejected or failed\
**And** the contract offer is not marked as successfully validated\
**And** the rejection reason indicates schema or content validation issue\
**And** the failure is traceable in backend logs.

AC7 Duplicate or replayed submission

**Given** the Provider Contract Manager has already processed the same Consumer signed contract offer\
**When** the same signed contract offer is received again\
**Then** the contract offer is not processed as a new successful validation\
**And** the duplicate or replayed submission is detected\
**And** the situation is traceable in backend logs.

AC8 Technical error during validation

**Given** the Provider Contract Manager has received the usage contract offer signed by the Consumer\
**When** a technical error occurs during asynchronous validation\
**Then** the validation result is marked as failed or remains pending according to the agreed lifecycle\
**And** the contract offer is not marked as successfully validated\
**And** the failure is traceable in backend logs.

AC9 Missing contract offer data

**Given** the asynchronous validation process is triggered\
**When** the required contract offer data is missing\
**Then** the validation result is marked as rejected or failed\
**And** the contract offer is not marked as successfully validated\
**And** the rejection reason indicates missing contract offer data\
**And** the failure is traceable in backend logs.

AC10 Asynchronous validation model

**Given** the validation process is implemented asynchronously\
**When** the validation is triggered\
**Then** the final validation result is not expected to be returned synchronously in the triggering request\
**And** validation must be verified through persisted backend state, contract negotiation status, validation result, logs or related contract details.

Technical info

The validation process is implemented as asynchronous backend processing.

Previous acceptance criteria expected synchronous API behaviour, but this does not match the implemented architecture.

Validation should therefore be tested by observing the resulting contract negotiation state, validation result and backend logs rather than expecting the final validation result in the same synchronous API response.

HTTP response codes in this story should not be treated as the primary validation mechanism unless a specific synchronous API endpoint is introduced or confirmed.

If PSO requires direct API based validation, the relevant OpenAPI endpoint must be confirmed separately.

This story is aligned with SIMPL 21948, which covers the reverse validation direction on the Consumer side.
