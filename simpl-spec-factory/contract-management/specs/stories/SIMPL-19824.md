# SIMPL-19824: [Replaced][API] - API to verify existing usage contract
- Status: DevTeam PBI In Progress
- Type: Story
- Created: 2025-10-22, updated: 2026-09-22
- Source: https://jira.simplprogramme.eu/browse/SIMPL-19824 (collected 2026-10-29)

## Description and acceptance criteria

**Why**: To prevent duplicate usage contracts for the same Consumer and resource description, ensuring contract integrity and avoiding redundant negotiations.

**What**:

**As a** Provider,\
**I want** to verify if a Consumer already has an active usage contract for a selected resource description from the data space catalogue\
**So that** I can avoid initiating a second contract for the same Consumer and resource

**Acceptance Criteria**:

*AC1 - No existing contract found*\
**Given** that a Consumer user is authorized to request a usage contract offer\
**And** the Consumer is allowed to access the requested resource based on the resource description’s access policies\
**And** I am a Provider handling the usage contract request\
**When** I verify the existence of a usage contract for this Consumer and resource description using the Contract Manager API\
**Then** the system returns an ACK (acknowledge) message with HTTP status code 200 (OK)\
**And** the asynchronous process of searching starts\
**And** no active contract exists\
**Then** the system sends a response to the dedicated endpoint\
**And** the response contains a JSON payload indicating no existing contract was found\
**And** the contract establishment process is continued

*AC2 - Active contract exists*\
**Given** that a Consumer user is authorized to request a usage contract offer\
**And** the Consumer is allowed to access the requested resource based on the resource description’s access policies\
**And** I am a Provider handling the usage contract request\
**When** I verify the existence of a usage contract for this Consumer and resource description using the Contract Manager API\
**Then** the system returns an ACK (acknowledge) message with HTTP status code 200 (OK)\
**And** the asynchronous process of searching starts\
**And** an active contract exists\
**Then** the system sends a response to the dedicated endpoint\
**And** the response contains a JSON payload indicating that an active contract already exists\
**And** the contract establishment process is prevented from proceeding

*AC3 - Invalid request parameters*\
**Given** that a Consumer user is authorized to request a usage contract offer\
**And** the Consumer is allowed to access the requested resource based on the resource description’s access policies\
**And** I am a Provider handling the usage contract request\
**When** I verify the existence of a usage contract for this Consumer and resource description using the Contract Manager API\
**And** the request contains missing or invalid parameters\
**Then** the system returns HTTP status code 400 (Bad Request)\
**And** the response contains a JSON payload with detailed validation error messages\
**And** the error event is logged\
**And** the contract establishment process is prevented from proceeding

*AC4 - Unauthorized*\
**Given** I am a Provider handling a usage contract request\
**When** I verify the existence of a usage contract for this Consumer and resource description using the Contract Manager API\
**And** the request contains an invalid, expired, or missing API key\
**Then** the system returns HTTP status code 401 (Unauthorized)\
**And** the response contains a JSON payload with detailed validation error messages\
**And** the error event is logged\
**And** the contract establishment process is prevented from proceeding

*AC5 - Invalid HTTP method*\
**Given** that a Consumer user is authorized to request a usage contract offer\
**And** the Consumer is allowed to access the requested resource based on the resource description’s access policies\
**And** I am a Provider handling the usage contract request\
**When** I verify the existence of a usage contract for this Consumer and resource description using the Contract Manager API\
**And** the HTTP method does not match the allowed methods for the endpoint\
**Then** the system returns HTTP status code 405 (Method Not Allowed)\
**And** the response contains a JSON payload with detailed validation error messages\
**And** the error event is logged\
**And** the contract establishment process is prevented from proceeding

*AC6 - Contract Manager API error*\
**Given** that a Consumer user is authorized to request a usage contract offer\
**And** the Consumer is allowed to access the requested resource based on the resource description’s access policies\
**And** I am a Provider handling the usage contract request\
**When** I verify the existence of a usage contract for this Consumer and resource description using the Contract Manager API\
**And** the Contract Manager API returns an error (e.g., service unavailable, timeout, internal error)\
**Then** the system returns HTTP status code 500 (Internal Server Error), depending on the error type\
**And** the response contains a standardized error message in JSON format\
**And** the error event is logged\
**And** the contract negotiation process is halted to prevent inconsistent contract states

**Technical Info**:\
* Response format in JSON\
**When** EDC calls the provider’s Contract Manager endpoint, it only receives an ACK as confirmation of receipt of the message. This is because the EDC behaves as a state machine. The actual response is sent later in a separate call: *“notify EDC":*\
[https://confluence.simplprogramme.eu/display/SIMPL/TCV+Dynamic+-+BP+07+-+Consumer+and+Provider+establish+a+usage+contract+for+selected+catalogue+items]\
* EDC Connector is used to ensure API availability and proper error handling\
* Endpoint: POST /agreements/\{contractNegotiationId}/search\
* HTTP Status Codes:\
200: OK\
400: Bad Request - missing or invalid parameters\
401: Unauthorized\
405: Method Not Allowed - the HTTP method does not match the allowed methods for the endpoint\
500: Internal Server Error - system errors

**Security & Compliance**:\
* Error messages must not reveal sensitive internal system information

**Additional Notes**:

On the EDC side need:\
* API: EDC - endpoint - to consume prepared response in defined and accepted format.
