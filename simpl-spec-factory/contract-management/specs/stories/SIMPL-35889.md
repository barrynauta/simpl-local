# SIMPL-35889: [API Definition] Create API for VC exchange
- Status: New Product Backlog Item
- Type: Story
- Created: 2026-10-27, updated: 2026-10-27

## Description and acceptance criteria

Functional description:\
Following the [API-First approach](https://confluence.simplprogramme.eu/display/SIMPL/API-First+Approach), this task extends the EDC API for Verifiable Credential exchange

Technical description:\
To support the implementation of SIMPL-35888 this task will add required endpoint to the EDC API.

Acceptance Criteria\
- The API specification is available and complies with the [API Guidelines](https://confluence.simplprogramme.eu/display/SIMPL/API+Guidelines)\
- Compliance is verified using the ITB for the rules for which a test case exist in the ITB.\
- Rules for which as test case is not available in the ITB can be verified manually.\
- A visual overview of the resources and their relationships is available\
- All the resources listed in the API specification should appear on the diagram.\
- Mocks and Stubs Can Be Generated Automatically\
- The spec enables generation of mock servers and client stubs using tools such as Microcks.\
- Example payloads are included for requests and responses to support meaningful mocks.\
- Accessible, Versioned and Traceable Artifact\
- The API spec is published in a [GitLab](https://code.europa.eu/simpl/simpl-open/).\
- The API spec is stored in YAML format.\
- Versioning follows [API Guidelines](https://confluence.simplprogramme.eu/display/SIMPL/API+Guidelines) versioning standards.\
- Ready for Collaboration and Automation\
- The API spec supports early collaboration across frontend/backend through mocks or contract sharing.\
- It is compatible with CI/CD pipelines.

|1|The contract-first principle SHOULD be followed when developing an API. In this approach, the specifications of the REST API are created first and not generated from the code. More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-ctr-first).| |\
|2|Specifications of the API SHOULD be provided using [OpenAPI 3.0](https://github.com/OAI/OpenAPI-Specification/blob/master/versions/3.0.3.md). More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-oas-contra). |3|Path segments and query parameters within an API SHOULD use lowerCamelCase notation to enhance readability and to separate compound names. As lowerCamelCase is used for JSON property names as well, the casing is consistent throughout the API. Trailing slashes MUST NOT be used. More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-uri-notat).| |\
|4|The URI SHOULD NOT contain a file extension. More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-uri-extens).| |\

|7|The HTTP response status code SHOULD be returned that best describes the outcome of the treatment of the request. More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-stat-codes).| |\
|8|Following guidelines SHOULD be respected when determining a name for a JSON property:\
- use lowerCamelCase notation;\
- also for abbreviations: all letters after the first should be lowercase.\
- use American English;\
- do not use underscores (_), hyphens ( - ) or dots (.) in a property name, nor use a digit as first letter;\
- don’t use overly generic terms like `info(rmation)` and `data` as property name or as part of it;\
- the name should refer to the business meaning of its value in relation to the object in which it is specified, rather than how it is defined;\
- omit parts of the name that are already clear from the context.\
Properties used from other standards, like OpenID Connect and OAuth2, are allowed to deviate from this rule. More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-jsn-naming).| |\

|10|Kebab-Case with uppercase SHOULD be used for HTTP header names. More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-hdr-case).| |\
|11|The API SHOULD match the following: URI = `{}https://{`}host`{}/{`}pathPrefix`{}/{`}apiName`{}/v{`}majorVersion`{}/{`}resources. More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-uri-format).\
- [https://](https://%2A/) - Services are at least secured on transport level using a one-way TLS connection. The implicit port is 443.\
- host - Hostname is determined by the environment where the service is deployed\
- pathPrefix - Optional path prefix to discriminate between REST APIs and other resources on the same host. (example: /REST)\
- apiName - Name of the API that groups a functional consistent set of resources. The API name consists of one or multiple path segments and SHOULD be written in lowerCamelCase (example: /referenceData/geography)\
- majorVersion - Major version numbers are integers and start at 1. See API versioning.\
- resources - All path segments identifying the actual resources.| |\
|12|Resources should follow the following 3 resource archetypes. More details [here](https://www.belgif.be/specification/rest/api-guide/#resource-archetypes).\
- Document\
- Collection\
- Controller | |\
|13|Resource name SHOULD NOT include ownership words (e.g. "own", "my", ...). Exceptions are to be made when the said ownership word is part of a technical term (e.g. "selfDescription").| |\

|15|The version string of an API SHOULD contain a major, minor and optionally a patch number. Only the major version of the API is part of the base URL (`{}basePath{`} in Swagger) of the API. Thereby, for a major version only a single minor and patch version can be available in production at a time. The version of the API MUST be included in the `info` section of the OpenAPI definition. More details [here](https://www.belgif.be/specification/rest/api-guide/#api-versioning).| |\
|16|REST clients SHOULD specify the media type(s) that is(/are) acceptable for the response in the Accept HTTP header. A REST response or request with payload MUST include the Content-Type HTTP header to indicate the media type of the HTTP payload. More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-cnt-negot).\
- Status code 406 MUST be used to indicate that the requested media type could not be provided.\
- Status code 415 MUST be used to indicate an unsupported media type in the request payload.\
- If a resource supports multiple content types through negotiation, the response header Vary: Accept MUST be added to avoid undesired cache hits.| |\

|23|Following naming guidelines should be applied when using an identifier or code in a REST API:\
- JSON property:\
- within an object that represents the entire or part of a resource: use id or code\
- to reference a resource within another one’s representation: property name should designate the relation between the resources; no need to suffix with id or code\
- path parameter: use id or code, OPTIONALLY prefixed with the resource type to disambiguate when there are multiple identifiers as path parameters\
- query search parameter: use same name as the property in the JSON resource representation of the response\
- OpenAPI type: add suffix Id or Code to distinguish it from the type of the full resource representation\
**As an** exception, use the standardized name for the business identifier if one exists, rather than id or code.\
If multiple identifiers or coding schemes may be used within the same context, a suffix can be added to the name to disambiguate.\
More details [here](https://www.belgif.be/specification/rest/api-guide/#rule-id-name).| |\
|24|Parameters should be described by specifying name, location (in), data type (defined by either schema or content) and other attributes, such as description or required.```\
paths:\
/users/{userId}:\
get:\
summary: Get a user by ID\
parameters:\
- in: path\
name: userId\
schema:\
type: integer\
required: true\
description: Numeric ID of the user to get```\
While the format and allowed values are by default defined by the data type, if a parameter only allows certain set of values, it should be restricted by adding the enum to the parameter’s schema. The enum values must be of the same type as the parameter data type.```\
parameters:\
- in: query\
name: status\
schema:\
type: string\
enum:\
- available\
- pending\
- sold ```| |\
|25|Required request parameters should be explicitly marked as such using "required: true" keyword.```\

name: userId\
schema:\

```\
Note that path parameters must have "required: true", because they are always required. | |
