# SIMPL-21966: Provider notifies Consumer about incorrectly signed usage contract offer
- Status: DevTeam PBI blocked
- Type: Story
- Created: 2025-12-08, updated: 2026-10-20
- Source: https://jira.simplprogramme.eu/browse/SIMPL-21966 (collected 2026-10-29)

## Description and acceptance criteria

Clarified Description

**As a** Provider,\
**I want** to notify the Consumer when the signed usage contract offer received from the Consumer is incorrectly signed or cannot be validated,\
**So that** the Consumer is informed that the contract establishment process cannot continue with the submitted signed offer.

This story covers sending an email notification from Provider to Consumer when Provider-side Contract Management detects an issue during validation of the signed usage contract offer.

The notification must be sent by reusing the existing SIMPL Notification Service.

Contract Management must not implement its own email sending mechanism.

Expected flow\
- Consumer sends the signed usage contract offer.\
- Provider-side Contract Management receives and validates the signed contract offer.\
- Validation detects that the contract offer is incorrectly signed, invalid or cannot be accepted.\
- Contract Management prepares a notification request/event for the Consumer.\
- The request/event is sent to the existing SIMPL Notification Service flow.\
- Notification Service sends the email notification to the Consumer.\
- The notification action is logged with correlationId where available.

Out of scope\
- Building a new Notification Service.\
- Implementing a custom email sender in Contract Management.\
- Implementing email templates from scratch unless required by Notification Service integration.\
- Validating the full signed contract flow itself.\
- Accepting or rejecting the original unsigned contract offer.\
- Delivering the fully signed contract.\
- Consumer UI review of the original human-readable contract offer.

Acceptance Criteria

AC1 Notification request is created and sent after failed signed contract validation

**Given** Provider-side Contract Management validates a signed usage contract offer received from the Consumer\
**When** the validation detects that the signed usage contract offer is incorrectly signed, invalid or cannot be validated successfully\
**Then** Contract Management creates a notification request for the Consumer\
**And** the notification request contains business context indicating that the signed usage contract offer could not be validated successfully\
**And** the notification request contains the recipient context derived from the contract negotiation / participant context\
**And** the notification request contains correlationId where available\
**And** the notification request is sent to the SIMPL Notification Service according to the agreed Notification Service integration contract.

AC2 Consumer recipient is resolved from contract context

**Given** a notification request needs to be sent to the Consumer\
**When** Contract Management prepares the notification request\
**Then** the Consumer recipient context is resolved from the contract negotiation / participant context\
**And** the notification request is prepared for the resolved Consumer recipient according to the agreed Notification Service integration contract.

AC3 Recipient cannot be resolved

**Given** Contract Management cannot resolve the Consumer recipient\
**When** the notification request cannot be completed\
**Then** the failure is logged with correlationId and error information where available\
**And** no invalid notification request is sent to the Notification Service.

AC4 Notification Service accepts the notification request

**Given** Contract Management sends the notification request to the SIMPL Notification Service\
**When** the Notification Service accepts the request\
**Then** Contract Management records the successful handoff with correlationId where available\
**And** the notification request is treated as successfully handed over to the Notification Service.

AC5 Notification Service rejects or fails the notification request

**Given** Contract Management sends the notification request to the SIMPL Notification Service\
**When** the Notification Service returns an error or the notification request cannot be handed over\
**Then** the failure is logged with correlationId and error information where available\
**And** the failure is handled according to the error handling / retry behaviour defined by the agreed Notification Service integration contract.

AC6 Notification delivery is handled by Notification Service

**Given** the notification request has been successfully handed over to the SIMPL Notification Service\
**When** the notification is processed further\
**Then** actual email / message delivery is handled by the Notification Service\
**And** Contract Management does not implement its own email sender or custom notification delivery mechanism.

Technical Notes

The trigger for this notification is the validation failure outcome produced by Provider-side Contract Management during validation of the Consumer-signed usage contract offer.

The validation logic itself is covered by SIMPL-19933 and SIMPL-19943. SIMPL-21966 should not retest the full validation logic.

This story covers only the Contract Management-side preparation and handoff of the notification request to the SIMPL Notification Service.

The final Notification Service integration mechanism, request/response contract, supported payload fields, error responses and retry behaviour must follow the agreed Notification Service contract defined under SIMPL-29268.

Contract Management must not implement a direct SMTP integration, custom email sender or its own notification delivery mechanism.

Recipient contact details must not be hardcoded in Contract Management. This is a technical implementation constraint and may be verified through implementation/configuration review where required.

Notification Service integration

This story reuses the existing SIMPL Notification Service.

The integration with Notification Service is asynchronous and Kafka based. It is not a dedicated REST endpoint exposed by Contract Management.

Notification Service AsyncAPI:\
[https://code.europa.eu/simpl/simpl-open/development/contract-billing/notification-service/-/blob/main/docs/asyncApi/asyncapi.yaml](https://code.europa.eu/simpl/simpl-open/development/contract-billing/notification-service/-/blob/main/docs/asyncApi/asyncapi.yaml)

Contract Management should publish an EmailNotification message to the existing notifications Kafka topic.

The Notification Service consumes the message and sends the email notification to the Consumer.

The EmailNotification payload must remain compliant with the existing Notification Service AsyncAPI schema.

The EmailNotification payload should contain only fields supported by the Notification Service AsyncAPI schema, such as:\
channel\
to\
cc\
subject\
message

The business context for this notification should be reflected in the subject and/or message body where appropriate.

Additional technical context such as contractNegotiationId, participant IDs and correlationId should be available in Contract Management logs and/or message metadata where supported by the integration.

If PSO requires these fields as dedicated attributes in the Kafka message payload, this should be handled as a separate change to the Notification Service AsyncAPI contract.
