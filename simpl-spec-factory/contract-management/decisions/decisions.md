# Decisions: contract-management (step 30a)

Closes the gaps that steps 20 and 23 found, so that the test writer and the code writer build the same thing. The spec owners were not available: every decision says what they should confirm. Full text, options and basis per decision are in [`decisions.json`](./decisions.json); the terms and state tables in [`glossary.md`](./glossary.md). Findings: [`ac-findings.json`](../validation/ac-findings.json) (`F-`), [`domain-findings.json`](../validation/domain-findings.json) (`D-`).

**Totals:** 33 decisions (25 on findings, 8 environment choices): accepted risk 4, follows the specs 1, provisional 28. All 20 blockers closed (F-005 and F-013 as accepted risk); all 47 majors have a default; 34 glossary terms decided.

## Source hierarchy

When sources disagree, the first one in this list wins. It applies to every decision.

1. **These decisions.** They are the only place where a conflict is settled for the build.
2. **The newest live story for a step.** The October 2026 R17 stories (SIMPL-35440 to 35889) win over older stories for the same step, and a story marked "Replaced" or "New proposed: Replaces" loses to its replacement. Why: they name the current technical architecture and the published endpoints, and the older ones say they are replaced.
3. **Acceptance criteria for behaviour** (what happens, in which order, what is stored, which callback is made). Why: they are what a tester checks.
4. **The OpenAPI for the wire format** (method, path, status code, schema and enum names) where it defines the operation. Story wire details count only for operations that are not in an OpenAPI. Why: the OpenAPI is the published contract that other components call.
5. **Technical notes in the stories** for the order of internal steps and the collaborators.
6. **The CDM** for ownership of concepts (external or own). It is in review, so it does not override 2 to 5.
7. **The business process** for meaning and for the business terms. For names, the business process comes first (DDD-01): business terms are used in tests and new names, published wire names stay as they are with a mapping in the glossary.

Where all sources are silent, the decision takes what is simplest to build and test, and says so.

## States and terms

| Id | Topic | Decision | Status | Closes |
|---|---|---|---|---|
| D12 | One state machine for the usage contract | The Contract Manager holds one usage contract record per contractNegotiationId and side, with one state machine; the offer is its first phase. States and wire values (ContractAgreementData.status): Requested = CREATED; Signed (the signed usage contract offer, Consumer side only) = FINALIZING; Active (the signed usage contract, both signatures, validated) = FINALIZED; Closed (ended without a usage contract: rejected, expired or failed validation) = TERMINATED. INITIATED appears only in acknowledgements, never as a stored state. Transitions: Requested to Signed (D5 accept), Requested to Closed (D5 reject, D13 timeout, D7 rejection), Requested to Active (Provider side, D7), Signed to Active (D8 success), Signed to Closed (D8 failure). The contract-ui-be offer has its own value set, as a view of the user decision: Requested = CREATED, Accepted = ACCEPTED (set only after the Contract Manager accept call succeeded), Rejected = REJECTED, Expired = EXPIRED (new value, D13). The contract-manager-be ContractOffer enum value APPROVED is not used by any operation in this build and is retired in favour of ACCEPTED. The UI labels are the state names in the glossary state tables. Suspended, Revocation requested, Revoked, Reactivation requested and Terminated are reserved states of the Active phase and are not built (D15). | provisional | F-004, D-005, D-006, D-007, D-009, F-018 |
| D13 | Timeout of unsigned offers in contract-ui-be | A scheduler in contract-ui-be runs on a cron expression (default daily at 01:00) and selects offers in CREATED whose creation time is older than the timeout (default 7 days, E6). Only CREATED counts as pending; every other status counts as finalized and is left alone. For each selected offer it calls the Contract Manager PATCH /contractOffers/{contractNegotiationId}/reject; on success it sets the offer to EXPIRED (label 'Expired'). If the call fails, the offer stays CREATED, the failure is logged and the next run tries again. The Contract Manager handles the reject as in D5 (Closed, /signed false). 'Terminated' is not used for offers: SIMPL-35692/AC4 is met by status EXPIRED in GET /contractOffers. | provisional | F-037, D-008 |
| D14 | Offer overview and details through contract-ui-be | GET /contractOffers returns 200 with a JSON array of ContractOffer (an empty array when there is none, never 404). GET /contractOffers/{contractNegotiationId} returns one ContractOffer or 404. ContractOffer gets these extra properties: contractNegotiationId and createdAt (read only), assetId, providerId and consumerId (sent by the Contract Manager in D4). The overview columns map to: Contract negotiation ID = contractNegotiationId, Resource description ID = assetId (D23), Resource name and Provider name = shown inside humanReadable only, Status = status with the D12 label. Filtering is a frontend concern and is not built. PATCH /contractOffers/{contractNegotiationId}/{operation} (accept or reject) is allowed only for CREATED (409 otherwise, 404 unknown); it calls the Contract Manager (D5) and on success sets ACCEPTED or REJECTED and returns 200 with the new status as a JSON string. If the Contract Manager call fails, the offer stays CREATED and the response is 502 problem detail. Usage contracts after acceptance (Signed, Active) are read from the Contract Manager GET /agreements/{contractAgreementId}, not from contract-ui-be. | provisional | F-044, F-045, F-046, F-051 |

## Questions for the owners, by impact

Highest impact first: the first ones change what is built and tested on the main path.

1. **Target flow (D1).** Confirm that the R17 stories (SIMPL-35526, 35584, 35660, 35677, 35440, 35692) are the target, and close SIMPL-19824, 19829, 22690 and 19934. Keep SIMPL-19933 and 21948 only for their checks and reasons.
2. **One state machine (D12, D13).** Confirm the states Requested, Signed, Active, Closed (and the reserved lifecycle states), their mapping to CREATED, FINALIZING, FINALIZED, TERMINATED, the new EXPIRED value in contract-ui-be, and the rename of APPROVED to ACCEPTED.
3. **Lifecycle after Active (D15, accepted risk).** Which backend owns revoke, suspend, reactivate and terminate, through which channel a change reaches the other participant, and how resource access is removed and restored.
4. **Provider validate and sign (D7).** Add validateAndIssue to the OpenAPI: synchronous, 201 on success, 422 with a rejection reason, 500 on a technical error. Should a Provider-side rejection call /isValid, /signed or both?
5. **Side of /create and of the existence check (D4, D3).** Confirm /create on the Consumer side, and say on which side the existence check runs (BP 7.2.2 and SIMPL-35858 disagree). Is SIMPL-32509 withdrawn?
6. **Wire format of accept and validation (D5, D8).** Confirm PATCH with 200 for accept and reject, and PUT with 200 and an asynchronous result for /verifications; can the VC body of VerifyCredentialRequest go?
7. **Identity and names (D19, D20, D21).** Confirm contractNegotiationId as the identity of the usage contract and the EDC agreement id as contractAgreementId; plan the rename of the CDM class to UsageContract and of the paths.
8. **Validation rules (D9).** Confirm the Provider-side reason codes, FAILED without retry, the duplicate rule (409 on an Active or Closed record) and the VC validity dates as the contract validity period.
9. **New endpoints (D10, D17).** Add GET /verifications/{contractNegotiationId}/vc and GET /audits/usageContractStatusCounts to the OpenAPI; describe the audit rule package.
10. **Overview data (D14, D23).** Which API serves usage contracts after acceptance, and where resource description id, resource name and Provider name come from.
11. **Notification Service contract (D11, accepted risk).** Publish the integration contract (topic or endpoint, payload, retry).
