# Decisions (step 30a): catalogue

Decisions that close the findings of steps 20b ([`ac-findings.json`](../validation/ac-findings.json)) and 23b ([`domain-findings.json`](../validation/domain-findings.json)) for the catalogue build. Full text, options and basis per decision are in [`decisions.json`](./decisions.json); the final glossary is in [`glossary.md`](./glossary.md). The spec owners were not available, so most decisions are provisional and carry a question for the owner.

## Source hierarchy

When sources disagree, the higher one wins:

1. These decisions.
2. Live acceptance criteria, for behaviour. Struck text never applies, but a later strike shows the owner's intent and is used as such (D29).
3. The entry OpenAPI files, for the wire: paths, field names, status codes, error bodies. Where a contract has a gap (an operation not yet defined), a decision fills it in the same style.
4. Technical details, notes and hints in the stories.
5. The CDMs in `sources.yaml`, for names and ownership.
6. The business processes BP05B and BP06.
7. Non-entry API files (catalogue-client-be v1, `*-itb`), only as context when the entry files have nothing (D23, D32).

Why: criteria are what the tests check; the OpenAPI is what the code must serve; notes are design hints from one moment; the CDMs and processes are drafts and broader than this build. The `API-`, `DDD-` and `SEC-` rules shape every new or changed contract.

### Naming

| Id | Topic | Decision | Status | Closes |
|---|---|---|---|---|
| D6 | Resource description is the one business name | The business term is resource description in all texts, tests, new operations and new schemas. New paths use resourceDescriptions. Existing wire names that say SelfDescription or selfDescriptions stay unchanged as documented legacy names (mapping in the glossary). The searching actor is the Consumer in every test name and UI text. | provisional | D-001, F-064 |
| D7 | One identifier for a resource description | A resource description is identified by its credential subject id (a DID such as did:web:...:DataOffering:...). The same value is claimsGraphUri[0] in a search result item, selfDescriptionId in catalogue-be and catalogue-client-be paths, and resourceDescriptionId in adapter paths. A detail call with that id returns the latest published version. Versions are addressed by version number only through GET /self-descriptions/{selfDescriptionId}/versions. sdHash and resourceKey are not used by the build. The catalogue identifier is one value named catalogueId (catalogueIds for a list); catalogue-client-be GET /selfDescriptions/{selfDescriptionId} requires catalogueId for own and federated details, and the own catalogue uses the configured own catalogue id (E3). | provisional | D-002, F-047 |
| D8 | Overall quality score and classification field names | Business terms: overall quality score and overall quality classification. Wire names: overallScore and overallClassification in every search result item of catalogue-be, the adapter and catalogue-client-be. overallCategory in SIMPL-29292/AC3 and SIMPL-29293/AC3 means overallClassification. The v1 names qualityScore and qualityClassification are not used. Inside the stored record the CDM names (qualityScore, qualityClassification) stay; the mapping is in the glossary. | provisional | D-003 |
| D9 | Federated catalogue only means a Trustor catalogue | Federated catalogue means a catalogue of a Trustor data space. The catalogue-be service is called the catalogue service in all texts and tests. The own data space catalogue is the own catalogue (local catalogue retired). | provisional | D-004, F-019 |
| D10 | The three meanings of active | Resource description: published (stored value active, see D18). Metadata Quality Profile: active Metadata Quality Profile, meaning the profile resolved for the latest published schema version (kept, it is the API path). Catalogue: federation enabled or federation disabled, on the wire CatalogueInfo.active true or false. Trusted, still enabled and authenticated in the stories all mean federation enabled. | provisional | D-006 |
| D11 | Quality Assessment Record representation and part names | The stored Quality Assessment Record is the JSON-LD graph returned by the Quality Scoring Service and exposed unchanged by GET /self-descriptions/{selfDescriptionId}/qualityAssessmentRecord. The structured qualityAssessment in the publication response is a projection of it. The catalogue-be schema names (SelfDescriptionQualityOverallResult and the others) stay as the catalogue read model; their mapping to OverallQualityRating, DimensionRating and RuleOutcome is in the glossary. The threshold source is called the Metadata Quality Profile everywhere (metadata quality definition and Minimum Quality Profile retired). | provisional | D-007 |
| D12 | Resource type and offering type are two concepts | Offering type is the closed set data, application, infrastructure (lower case) on a resource description (offeringType in search items). Resource type is the Schema Manager open value on a schema; the catalogue passes it through unchanged and never validates it. Since schema management is out of scope (D1), no catalogue test depends on resource type spelling. | provisional | D-008 |
| D13 | Search scope and main properties | The catalogue selection of a search is the search scope: a list of catalogueId values (catalogueIds). The main properties of a resource description in an overview are the general service properties summary: name, description, offeringType, inLanguage and serviceAccessPoint, plus overallScore and overallClassification for own-catalogue results. The result item is called resource description summary; its wire names are those of the search item n. | provisional | D-014, D-011, F-039 |

### Quality

| Id | Topic | Decision | Status | Closes |
|---|---|---|---|---|
| D14 | Score scale | Every score on the wire (overallScore, dimension scores, thresholds, score ranges, minimumScore) is a fraction from 0 to 1. minimumScore below 0 or above 1 gets 400 invalidInput. The UI shows scores and accepts the minimum score as a percentage from 0 to 100 (whole numbers or one decimal) and sends the value divided by 100. The examples with minimumScore 75 are read as 0.75. | provisional | F-004 |
| D15 | Source and order of classifications | Advanced search with a selected schema: the UI lists the overall classifications of that schema's active Metadata Quality Profile. Quick search and the SEARCH-schema form: the UI lists the union of overall classification labels of the active profiles of all published RESOURCE schemas, deduplicated by label and ordered by lower bound. The backend evaluates the filter per result with the profile recorded in that result's Quality Assessment Record: a result passes if the lower bound of its classification range is at least the lower bound of the selected label in that profile. A result whose profile lacks the label is excluded. Ranges include their lower bound and exclude their upper bound, except the top range, which includes 1. Labels compare case-insensitively. A label that is in no active profile gets 400 invalidInput. | provisional | F-005, F-006 |
| D16 | Unscored results and invalid filter input | With minimumScore or minimumClassification set, resource descriptions without a Quality Assessment Record (overallScore null) are excluded. Without any quality filter they are returned. The UI validates the score field (number, 0 to 100) inline and disables the search button while invalid. The API returns 400 invalidInput for an out-of-range score or unknown classification. | provisional | F-007 |
| D17 | Publication quality gate outcomes | POST /self-descriptions/resource calls the Quality Scoring Service synchronously, using the active Metadata Quality Profile of the resource description's schema. Pass: 201, stored and published, QAR stored. Quality failure: 422, not stored, Error body code QUALITY_THRESHOLD_NOT_MET and message 'Quality Score X is below threshold Y.' for the overall score, or 'Dimension D score X is below threshold Y.' for the first failing dimension (scores as fractions with two decimals). Technical failure (scoring service unreachable or timing out after 10 seconds, invalid or unparsable QAR, no active profile, missing threshold): 500, not stored, Error body code QUALITY_ASSESSMENT_FAILED, and one ERROR log line with the resource description id and the reason. Tests check the status, the body and that a following GET returns 404; they do not check the log. | provisional | F-001, F-002, F-003 |
| D18 | Resource description lifecycle | States: published (stored value active) and revoked. Publication is synchronous: 201 or an error, no pending state, so the 202 response is not used. Publishing a new version revokes the previous published version of the same resource description. Revoke moves published to revoked; revoking a revoked one is a no-op with 200. Search and detail return published versions only. Deletion is outside the lifecycle and not built (D4). | provisional | D-005 |

### Search

| Id | Topic | Decision | Status | Closes |
|---|---|---|---|---|
| D19 | Matching rules for quick and advanced search | Quick search: the search string is split on whitespace into terms; a resource description matches if at least one term is a case-insensitive substring of at least one literal value of its credential subject. Advanced search: each criterion is matched against its own property; strings match by case-insensitive substring, numbers and dates by equality or by the operators op1 and op2 of the range filter, enumerations by case-insensitive equality; all criteria must match (AND). | provisional | F-026, F-027 |
| D20 | Search authorisation and discovery access policy | Tier 1: no token gets 401, a token without the role CATALOGUE_SEARCHER gets 403. Tier 2: the User-Attributes header carries the Consumer's identity attribute codes, comma separated. Resource descriptions whose discovery access policy is not met are left out of a result list silently (never a 403 for the whole search). Identity attributes and their federation mapping are owned outside the catalogue (IAA and the gateway); the discovery access policy belongs to the resource description. A missing User-Attributes header on a Trustor operation gets 400; an attribute without mapping counts as absent. | provisional | F-029, D-010, F-024, F-059 |
| D21 | How a discovery access policy is represented | Assumption for the build: a resource description lists the identity attribute codes allowed to discover it; a Consumer meets the policy if User-Attributes contains at least one of them; an empty or missing list means everyone with the search role may discover it. Test fixtures set this list explicitly. | accepted risk | D-010 |
| D22 | Own catalogue in a search | Each data space has exactly one own catalogue, so the local quick search needs no catalogue parameter. The own catalogue is searched only when the Consumer selected it. The UI preselects the own catalogue; the Consumer may deselect it if at least one Trustor catalogue stays selected. | provisional | F-028, F-035 |
| D23 | Catalogue list for the selector | catalogue-client-be exposes GET /catalogues exactly as in the v1 file (CatalogueInfo id, name, authorityURL, active), added to the v2 contract. The selector shows the own catalogue first (configured id and name, E3), then every Trustor catalogue with active true; catalogues with active false are not shown. With no Trustor catalogues, only the own catalogue is offered and the text 'No federated catalogues are available.' is shown. If GET /catalogues fails, the Trustor part is not populated, the own catalogue stays selectable, and the message 'The list of catalogues could not be loaded.' is shown. | provisional | F-018, F-019, F-021 |
| D24 | Federated search returns one grouped response | When at least one Trustor catalogue is selected, the UI makes one call: catalogue-client-be forwards it to the adapter GET /governanceAuthority/selfDescriptions or POST /governanceAuthority/selfDescriptions/advancedSearch, with catalogueIds holding all selected catalogues, the own catalogue included if selected. The response changes from the flat list to {groups: [...]}, one group per selected catalogue in request order, each {catalogueId, catalogueName, authorityUrl, status, totalCount, items, page, pageSize, totalPages}. To page one group, the client repeats the search with only that catalogueId and the wanted page; other groups stay as they are on screen. When only the own catalogue is selected, the existing local search operations are used unchanged. In a mixed advanced search all catalogues, the own one included, are searched with the SEARCH schema fields. The UI shows one tab per group, own catalogue first, tab label the catalogue name. | provisional | F-033, F-034, F-038, F-061 |
| D25 | Failing Trustor in a federated search | A failing Trustor never fails the whole search. If the call to a Trustor fails (TLS handshake failure, connection error, 403, 5xx, or no answer within 10 seconds), its group has status unavailable and an empty items list; the response is still 200 and other groups are unaffected. A group that searched fine has status complete, also when empty. A catalogueId that is not in the catalogue list gets 400 invalidInput for the whole request. A listed catalogue with federation disabled gets status unavailable without a call. At the Trustor, a caller with a valid certificate but no enabled federation gets 403 from the gateway; a revoked certificate fails the handshake. Both are gateway behaviour (D27) and reach the Trusted side as a failed call. | provisional | F-030, F-031, F-032, F-036, F-023 |
| D26 | Quality in federated groups | Items in Trustor groups carry overallScore and overallClassification as null, and the quality filter is applied only to the own catalogue group; Trustor groups ignore it. Own-catalogue overviews show the overall quality score (as percent) and classification. Sorting of overviews is not built (no criterion). | provisional | F-037, F-040 |
| D27 | What the gateway does and what the adapter does | Mutual TLS, Trusted GA authentication, the federation check and identity attribute mapping are done by the gateway in front of the Trustor adapter, as the adapter contract says. They are not built in the catalogue build. The adapter receives User-Attributes (already mapped) and Correlation-Id and applies the discovery access policy itself (D20, D21). Tests of the Trustor operations call the adapter directly with these headers. | provisional | F-050, F-023, F-024 |
| D28 | Trustor-side search operations | Add to the adapter tier 2 contract: GET /federated/resourceDescriptions (query catalogueIds, searchString, page, pageSize; headers User-Attributes and Correlation-Id) for quick search, and POST /federated/resourceDescriptions/advancedSearch (body advancedSearchRequestPayload without quality fields; same headers) for advanced search. Both return searchResponsePayload with overallScore and overallClassification null, 200 with an empty items list when nothing matches, 400 for missing headers or invalid input, 500 on failure. They search only the listed catalogues of the Trustor's own data space, using D19 and D21. | provisional | F-022 |

## Questions for the owners, by impact

1. **D24** (Federated search returns one grouped response): Confirm the grouped response shape and per-group paging by repeating the search for one catalogue.

3. **D29** (Schema for a federated detail): Confirm that SIMPL-31148, SIMPL-31770 and SIMPL-33885 drop the schema from the federated detail.

5. **D7** (One identifier for a resource description): Confirm that claimsGraphUri, selfDescriptionId and resourceDescriptionId are the same value, and that catalogueId stays required for own-catalogue details.
6. **D14** (Score scale): Confirm the 0 to 1 scale and the percent display in the UI.
7. **D21** (How a discovery access policy is represented): Provide the real discovery access policy format and where it sits in the resource description.
8. **D28** (Trustor-side search operations): Provide or confirm the SIMPL-31880 contract; align these paths with it.

12. **D17** (Publication quality gate outcomes): Confirm 422 and 500, the error codes, and that the threshold comes from the schema's active profile.
13. **D15** (Source and order of classifications): Confirm the per-result evaluation and the inclusive lower bound.
