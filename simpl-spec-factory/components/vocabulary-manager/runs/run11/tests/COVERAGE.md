### Decisions with no scenario

- **D2** (CDM snapshot): Input pinning of the CDM snapshot; no runtime behaviour.
- **D61** (SIMPL-28680 leaves the live set): SIMPL-28680 leaves the live set; its criteria are not in ids.json, so nothing to test (D1).
- **E3** (Store and stubs): Store choice and stubs; refined by E4 (no reset) and D83. No scenario of its own.
- **D80** (Personal data in logs): Log content (no e-mail or name in logs) is not observable through the API.
- **D81** (Several backend instances): Withdrawn by D82.
- **Q3** (Availability and recovery): Availability, recovery and the backup round trip are measured in the build and step 70, not through the API.
- **Q4** (Design load and scaling): Design load and seed: used by the load test (load/seed.py, 1000 vocabularies x 20 versions).
- **Q5** (Maintainability): Coverage, Trivy and query bounds are build measurements (step 70).
- **E6** (Reuse choices): Reuse choices; build review.
- **D83** (Store access): Store users, passwords and network placement are deployment facts, not observable through the API.
- **D87** (Model and contract deliverables): Build deliverables (logical and physical model, openapi-decided.yaml); checked by review, not by the suite.
- **D88** (Realm key refetch): Realm key refetch timing needs control over Keycloak keys; the decision itself says the identity provider cases are unit tests in the code (D44).
- **D89** (Restore and later writes): Backup and restore procedure; not an API behaviour (Q3 restore test runs in the build).
- **D92** (Concurrent uploads): A fifth parallel upload on one instance gets 503: the outcome depends on timing and on how many backend instances serve the API port (D102), so a black-box test cannot force it reliably. D119 keeps the suite's parallel test at 4.
- **D93** (Request validation against the contract): Choice of request validator, recorded in REUSE.md; build review.
- **D94** (Library choices): Library choices; build review.
- **D95** (Lint, format and UI tests): Lint, format and UI component tests on the finish line; build tooling.
- **D96** (Structured log fields): Log line format; not observable through the API.
- **D97** (CDM, licence and glossary in the build): Build inputs and deliverables (CDM, LICENSE, glossary); build review.
- **D98** (Local stack hardening): Local stack hardening (ports, networks, limits); deployment review.
- **D99** (Load test shape): Load test shape: checked by the load test (load/), not by a scenario.
- **D102** (Two backend instances): Two backend instances on the finish line; the suite runs against whatever API_URL serves, and the D43 parallel scenario holds for any number of instances (D82).
- **D103** (Circuit breaking): Circuit breaker timing (half of the last 20 calls, 10 s open) cannot be observed reliably from outside; the store-down scenarios check the 503 outcome.
- **D104** (Exception model): Exception model inside the code; the problem types it produces are checked through D48.
- **D105** (Simpl log format): Log format and shipping; not observable through the API.
- **D106** (Where file bytes live): Where the file bytes live; the byte-for-byte download scenarios check the effect (D29).
- **D107** (No host port for the store): No host port for the store; deployment review.
- **D117** (CDM findings): CDM findings and the logical model; build review.
- **D120** (Management port with replicas): Management port placement; deployment review.
- **D124** (Base IRI of external files): The base IRI of external files is not observable through the API: registration checks syntax only and returns 201 whatever base is used. The scenario 'Relative IRIs in an external file ...' only shows that relative IRIs are accepted (tagged D41).
- **D129** (Unknown key after a failed fetch): Unknown key id after a failed key fetch needs control over Keycloak availability; unit tests per D44.
- **D131** (Start command): Start command of the stack; used by the orchestrator, not by the suite.

## UI scenarios (step 60)

All 62 `@ui` scenarios are automated with Playwright for Python (`features/steps/ui.py`, `support/ui_hooks.py`) and run with `./run.sh ui` (behave JSON in `reports/ui.json`). No scenario is tagged `@manual`.

- Elements are found only by decided texts, labels, column headers, routes (D31, D74), the menu button names of D75, roles status and alert (D75, D90, D114, D115) and the regions of D75 and D90. Where a decision names an action but not its element type ('New Vocabulary +', 'Cancel'), a button or a link is accepted.
- The login uses Keycloak's own form (E1). Every scenario gets a new browser context, so no cookie, storage or Keycloak session is reused within or across runs.
- Error cases stub the API in the browser (D24, E3): only fetch and XHR calls whose path ends with the decided API path are answered by the stub.
- 'Selecting a version' (D35) is done by activating the version number in its row; no decision says how a version is selected, so the step accepts a link or button named with the number, or the first cell.
- Sortable columns (D23) are recognised by aria-sort or a button in the column header; no decision says how sortability is shown.
- axe runs with the browser's CSP bypass, as D123 asks.
- The four `@a11y` scenarios cover the main pages: list, details, create form and new version form. Keycloak's login page is not part of the build and is not checked.

Result against the run 11 build (20 Nov 2026): 61 of 62 passed; axe found 0 WCAG 2.1 AA violations on the four pages. One failure, a difference between the build and the decisions (not a test bug):

- `ui_status_access.feature:83` 'A user without a vocabulary role sees the authorisation message on the list' (D18, SIMPL-18195/AC2): for ga-norole the list shows 'The vocabulary list could not be loaded.' with the API detail of the 403. D18 says any 403 from the API shows 'You are not authorized to perform this action.'. D72 fixes the load error text only for 500 and 503.
