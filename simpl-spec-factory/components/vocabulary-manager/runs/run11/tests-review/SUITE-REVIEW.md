# Suite review

## 1. In short

- **Scenarios reviewed:** 544 in 18 feature files: 472 default API scenarios, 10 store-down scenarios and 62 `@ui` scenarios (Gherkin only until step 60). I also checked the step library, `support/vm.py`, the fixtures, `COVERAGE.md` and the load test.
- **Dry run:** clean. 0 undefined steps and 0 ambiguous steps.
- **Overall:** the API part is strong. Problem types, issue names, detail texts, the order of checks (D51, D63, D67, D139) and "nothing stored" proofs follow the decisions closely. Store independence (E4) is handled well.
- **Findings:** 14 in total.
  - By severity: 1 blocker, 1 major, 12 minor.
  - By kind: over-assertion 3, under-assertion 3, fragile 4, traceability 1, gaps 3.
  - No misreading and no proof that cannot work in the API scenarios. The blocker is a UI scenario that follows D5 and D100 together, and those two decisions conflict.

## 3. Questions for the decisions

1. **Q-1 (D5 against D100, SIMPL-18161/AC1):** SIMPL-18161/AC1 asks for the current version in each list row, and D5 names the UI column "Latest version". D100 lists the columns without it. Is there a "Latest version" column, and if so, where does it sit in D100's order?
2. **Q-2 (D4, D25, glossary):** what does `lastUpdateDate` mean on a version object? D4 fixes it only when a new version deprecates older ones. Does a manual PATCH of a version's status update that version's `lastUpdateDate`?
3. **Q-3 (D37, D46):** for a 409 on the create or new version form, does the message above the form show the problem detail as sent by the API, or a UI text? If it is a UI text, what is it?
4. **Q-4 (D51 for reads):** D51 orders checks on writes only. For GET operations, do query parameter checks (400) come before store access (503) and before 404? Does the role check (403) come before 404 on reads? The suite assumes both.

## Answers of the test writer (45b)

SR-01: fixed. I removed the "latest version 1" check, so the row is checked only against D100's columns. The D5 and D100 conflict (Q-1) is left for the owners.
SR-02: fixed. Both 409 UI scenarios now check one element with role alert above the form and that the form stays open. They no longer check the detail text, because D37 and D46 do not fix the wording.
SR-03: fixed. I dropped the `lastUpdateDate` check on the version PATCH response. The vocabulary GET check, which D25 fixes, stays.
SR-04: fixed. I retagged the scenario `@D21 @D22` instead of `@D51`; it is otherwise unchanged.
SR-05: fixed. The rows `Ab` and the 2-character name now prove nothing was stored with a list filter on the exact requested name. Names that break the filter pattern still fall back to the scenario-id filter.
SR-06: fixed. The API scenario now remembers both last update dates and skips itself when the two writes fall on different UTC days. The UI scenario now filters on the UTC date taken from Alpha's own creation date, not from the test clock.
SR-07: fixed. The step reads pages of 100 only until both names are found and checks their order there. It no longer sorts-checks the whole store.
SR-08: fixed. When a request over 5 MB ends in a connection reset, the scenario is now skipped as inconclusive instead of failing.
SR-09: fixed. The UI logins use role words ("a vocabulary viewer", "a vocabulary administrator", "a user without a vocabulary role"), and creator checks use `${EMAIL:admin}`.
SR-10: fixed. I took `@D124` off the scenario and retagged it `@D41`. `COVERAGE.md` now says D124 cannot be observed through the API.
SR-11: fixed. I added a create with 65 parts (400, nothing stored) and an external search with a bad array element (400, issue `namespaceUris[1]`). Both are tagged `@D110`.
SR-12: fixed. I added a search for `{name}` and `{name, version: 1}` with one version stored. It expects two results, `latest` true then false.
SR-13: fixed. I added a reference to `<contentBase>/content/` with no name, which expects `externalReferenceSkipped` (D69). I also added `Accept: application/*` on a content download, which expects 200 with `text/turtle` (D127).
SR-14: fixed. The truncation scenario now checks that issues for `c00000` and `c00999` are present and none for `c01000`, so it proves the first 1000 in file order are kept.

Dry run (`./run.sh dry-run`): 549 scenarios with 3457 steps. There are 0 undefined steps among the non-UI scenarios, every API step matches exactly one definition, and every tag is a known id. I regenerated `COVERAGE.md`.
