## UI automation (step 60)

- Browser steps: Playwright for Python (Chromium, headless) in `features/steps/ui_steps.py`; the browser is started in `features/environment.py` and every `@ui` scenario gets a fresh browser context. Elements are found by role, label and text; no test ids (the decisions name none).
- Login: the Keycloak form of the build is filled with the E1 user of the role; the session is kept per role in `.ui-state/` so later scenarios reuse it.
- API stubs (D24): `the API answers ... for the UI` fulfils the matching browser request under `UI_API_PREFIX` (default `/v1`, the path the UI calls through its nginx proxy) with a problem+json body.
- Rows that are not on the first list page (the shared store holds many vocabularies, E4) are found by typing the name in the 'Name contains' filter. 'Opens the create or new version form by its URL' uses the routes the app shows (`/vocabularies/new`, `/vocabularies/<Name>/update`).
- 'The actions menu offers [...]' checks that every listed action is there and that no write action outside the list is offered; the extra read action 'History' is allowed (D35 names it).
- 'An error message says' accepts an element with role alert or status (the scenarios do not fix the role).
- Accessibility: `ui_accessibility.feature`, one `@a11y` scenario per main page (list, details, creation form, new version form), axe-core through axe-playwright-python with the tags wcag2a, wcag2aa, wcag21a, wcag21aa. Results per page in `reports/axe/<page>.json`.

- `@manual`: none. Every `@ui` scenario runs in the browser.
