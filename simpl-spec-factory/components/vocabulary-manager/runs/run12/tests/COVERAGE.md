## UI automation (step 60)

`./run.sh ui` runs every @ui scenario in Chromium with Playwright for Python (`features/steps/ui_steps.py`), behave JSON to `reports/ui.json`, axe results to `reports/axe/`, screenshots of failures to `reports/ui-screens/`. Each scenario gets a new browser context, so no stored session or cookie is reused; sign-in goes through the Keycloak login form of E1.

Elements are found only by decided texts and names: labels and texts of D60, D72, D115; column headers of D23, D35, D159; 'Actions for <Name>' and 'Actions for version <n>', the regions 'Version <n>', 'Validation report' and 'Validation warnings' (D75); roles status and alert (D75, D90, D114); aria-current and aria-sort (D163); routes of D31 and D74; the /v1 API path of E2 for stubs. Nothing is taken from the build.

Interpretations of step texts (assumptions):

- 'the field X shows an error': the field has aria-invalid="true" and a non-empty error text tied to it by aria-errormessage or aria-describedby.
- 'no request was sent to the API': no POST, PATCH, PUT or DELETE to /v1/ after the click.
- 'the API answers <code>': a Playwright route on the browser context answers the matching method and /v1 path with a problem+json body (D24); 200 on GET /vocabularies gives the empty example of the OpenAPI.
- 'every action ... with the keyboard only': every visible, enabled focusable element is reached with Tab, and the first actions menu opens with Enter and closes with Escape.
- 'the page has no axe violations': axe-core rules tagged wcag2a, wcag2aa, wcag21a, wcag21aa.

@manual scenarios: none. Every @ui scenario could be automated with the decided names.
