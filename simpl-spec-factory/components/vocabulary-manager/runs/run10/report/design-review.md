**The five most important findings**

1. **Token validation is partly the build's own code (REUSE-01, MUST, partly).** Nimbus checks the signature. The claim checks for issuer, audience, expiry, not-before and subject are written by hand in `TokenValidator.checkClaims`, and `RealmKeyProvider` (150 lines) fetches and caches the keys itself. D108 allows own code only for the key-fetch timing. Nimbus `DefaultJWTClaimsVerifier` and Spring `JwtValidators` both cover the claim checks. REUSE.md says the claim checks come from Nimbus, which is not true.
2. **A second request layer runs beside Spring MVC (REUSE-06 and REUSE-07, partly).** It has its own route table (`ApiOperation`, 248 lines), its own 405 routing (`RoutingFilter`), its own 404, 406 and 415 checks (`MediaTypeFilter`, 110 lines), and a hand-written query-string parser (`QueryParameters`). Controllers read `HttpServletRequest` by hand and do no binding. The decided order of checks explains part of this. Still, about 800 lines of infrastructure duplicate what the framework does, and REUSE.md has no row for the routing and content-negotiation parts, although D93 requires one.
3. **Two resilience gaps (MSV-06 and ARCH-34, partly).** The circuit breaker ignores `StoreFailureException` (`ComponentConfig.circuitBreakerRegistry`). So if Fuseki answers 5xx because it is overloaded, the breaker never opens and callers get 500 instead of 503. Separately, the public `GET /v1/health` calls `keys.refresh()` directly (`HealthController.getHealth`), which skips the 10 s cooldown of D88. Any unauthenticated caller can trigger calls to the identity provider. Only the breaker limits them.
4. **CODE-11 (MUST) is not met and is not listed as a deviation.** No class depends on an abstraction. Services, filters and the health controller all depend on the concrete classes `VocabularyRepository`, `SparqlStore`, `RealmKeyProvider` and `TokenValidator`, which `ComponentConfig` wires directly.
5. **Four MUST rules are not met, and the build records each one:** OWT-A04 (HTTP everywhere, `sslRequired: none`, no encryption at rest), UX-01, OPS-37 and ARCH-07 (one Fuseki). Q1 is also not proven at the design load. The build is honest about all of these.

## 3. Disagreements with the build's own documents

1. **REUSE.md, token validation row.** It says signature and claim checks come from Nimbus. Only the signature does; `TokenValidator.checkClaims` is own code. This should be a REUSE.md row with a reason, or be replaced by Nimbus `DefaultJWTClaimsVerifier`.
2. **REUSE.md is incomplete under D93.** There is no row for `ApiOperation`, `RoutingFilter` or `MediaTypeFilter` (own routing, 404, 405, 406 and 415 handling). The "Front controller with a filter chain" pattern row does not replace the reuse row D93 asks for.
3. **REUSE.md patterns table.** It lists "Retry with back-off" for the write retry loop in `VocabularyService`. That loop re-reads and retries at once, with no back-off.
4. **DEVIATIONS.md is missing several rules that are not met:**
   - CODE-11 (MUST, no abstractions)
   - CODE-33 and CODE-44 (overridden by D104 but not recorded)
   - SEC-13
   - API-02
   - API-35 (the UI sends no Accept header)
   - ARCH-27 (pull only)
   - the alerting half of OWT-A09
5. **architecture.md and QUALITY.md on the key-fetch cooldown.** They present the 10 s refetch cooldown (D88) as holding. `HealthController.getHealth` calls `refresh()` directly, outside the cooldown, from an unauthenticated endpoint.
6. **QUALITY.md, "Bounded resources".** True for the API containers. The `store-tools` service has no limits, and the reference-check query allows 200 000 rows.
7. **Where I agree with the build.** It is accurate on Q1 (not proven at the design load), on the D98 management-port deviation, on the Keycloak brute-force protection (verified in the realm file), and on OWT-A04, UX-01, OPS-37 and ARCH-07.

## 4. Findings for the next run

1. **Narrow D108.** Exempt only the key-fetch timing. State that claim checks must use Nimbus `DefaultJWTClaimsVerifier` or Spring `JwtValidators`.
2. **Make D93 explicit about routing and content negotiation.** Either require Spring MVC mappings and produces/consumes with an ordering test for 404, 405, 406 and 415, or require a REUSE.md row naming Spring MVC as the alternative not taken. Ask the writer to bind query parameters with the framework rather than parse the raw query string.
3. **Settle D103's failure classes.** Say whether store 5xx counts as a breaker failure. Add a rule that no unauthenticated endpoint may trigger an outbound call outside the D88 cooldown.
4. **Add a step-50 check to the writer brief:** every decision that overrides a rule (D104, D17, D45) produces a DEVIATIONS.md row automatically. CODE-33, CODE-44, SEC-13 and ARCH-27 slipped through this way.
5. **Decide CODE-11 for this stack.** Either require interfaces for the store and repository ports, or record it as a deviation with a reason. It is a MUST and is now silently not met.
6. **Q1 load test.** Use an open-model driver (for example k6 or Locust with a constant arrival rate) so the offered rate actually reaches 20 reads/s. Budget time for the 1000 x 20 seed. Without this, Q1 stays unproven run after run.
7. **Ask for a short threat model in `docs/`** (STRIDE per trust boundary). It would settle SEC-01 and OWASP-05.
8. **Reword DATA-22 to DATA-25 for RDF stores** (for example "SHACL shapes per named graph count as the PDM") so they stop coming out as not applicable or partly.
9. **Small fixes:** an Accept header in the UI API client, limits on `store-tools`, and a smaller bound on the reference-check query (or a decision that justifies 200 000).
10. **D98, management port.** Either accept the port on the front network or give a concrete alternative (for example `management.server.address` bound to the store network interface).
